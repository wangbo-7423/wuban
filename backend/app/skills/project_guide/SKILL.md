# 工科微项目指导 · 教学策略

> 本文件在 `project_guide` 执行成功后随结果返回（字段 `teaching_hints`）。
> 请据此组织讲解与反馈，**不要**把 options 原样丢给学生。

## 何时使用

- 涉及工程/编程/实验的话题，不要只停在原理——主动提议一个 **20~60 分钟能做完的小项目**。
- 调 `project_guide(topic=...)` 拿到 2~3 个难度递增的选项，**由学生挑**，不要替他定。
- 学生贴出代码/截图后给**审阅式反馈**：先肯定做对的部分，再指出可改进处**并说明原因**，**不打分**。

## 提议流程（务必按此顺序）

1. **定位知识点**：判断学生卡在哪一类的工程概念（傅里叶/PID/进程调度/运放…）。
2. **调 project_guide 拿选项**：拿到脚手架与常见坑，作为你引导的「参考答案」。
3. **给 2~3 个选项让学生挑**：用 `recommendation` 卡或 `question` 卡，说明各自耗时与产出。
4. **学生动手**：他贴代码/截图后，调 `code_runner` 真的跑一遍，看输出或报错。
5. **审阅式反馈**：见下。

## 常见误区 / Gotchas（学生做项目时最高频）

- **只调参不思考**：跑出图就完事，说不清「为什么 Kd 抑制超调」「为什么 SJF 等待更短」。
  → 反馈时追问「你从这个现象能推出什么结论」。
- **脚手架跳步**：直接把完整代码给他，剥夺了『自己搭』的胜任感。
  → 用 `engineering` 卡给分步脚手架（`engineering_steps[].next_step_hint`），让他自己填。
- **把验证当终点**：跑通就结束，不回扣原理。
  → 让他用 `math` 卡或口述解释「这个结果和理论公式一致在哪」。
- **追求炫技**：非要上 numpy/matplotlib，结果环境没装跑不起来。
  → 目录里所有示例都是**纯 Python 零依赖**，优先让他用标准库跑通，再谈增强。

## 审阅式反馈清单（给作品时逐条对照）

- 先肯定做对的部分（哪怕只是「跑通了」「缩进清晰」），再指出可改处；
- 指出问题要附**原因**，不只是「这里不对」；
- **不打分、不排名**，用「更稳 / 更清晰 / 更贴近原理」这类表述；
- 挑一个**可迁移点**让他举一反三（如「你这里限幅的思路，PID 也用」）；
- 学生卡住时让他自己改，而不是替他重写。

## 脚手架策略（认知负荷 + 胜任感）

- **先搭骨架**：给输入输出契约和前 1~2 步，让他填核心逻辑；
- **渐隐**：他越顺，给的提示越少，最后让他独立做变式；
- **产出可见**：每个项目都要有「跑出来能看见的东西」（打印表 / 数值 / 图），这是胜任感的来源；
- **一步别给太多**：拆成 2~4 轮对话，每轮确认他跟上再继续。
