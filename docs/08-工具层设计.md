# 08 · 工具层设计：声明式注册 + 领域知识就地打包

> 上承 [07-上下文工程设计](./07-上下文工程设计.md)（Select / Compress 策略的落点）。
> 本文回答：**新增一个工具 / skill 时要动几处代码？为什么工具的「配套知识」
> 应该声明在工具自己身上，而不是集中在别处的表里？**
> 对应实现：`backend/app/agent/tools.py`（ToolSpec）、`backend/app/skills/base.py`（SkillSpec）。

---

## 1. 要解决的问题：耦合点散落

迁移前的结构里，「一个工具」的业务知识散落在 5 个文件，靠命名约定隐式关联：

| 业务知识 | 旧位置 | 问题 |
| --- | --- | --- |
| 工具是什么、何时用 | `tools.py` ToolSpec | ✓ 唯一该在的地方 |
| 属于哪些场景 | `intent.py` `INTENT_TOOLS` 白名单表 | 加工具要改这里 |
| 哪些字段算「结论」（压缩摘要） | `compress.py` `_DIGEST_FIELDS` 全局表 | 加工具要改这里 |
| 场景指南文件 | `prompts/guide_{intent}.md` 命名约定 | 加场景靠文件名对上号 |
| 任务状态提取 | `session_memory.py` 读卡片协议 | （卡片协议级，不在本文范围） |

后果：加一个 `plot_function` 要同时改 4 处，漏掉任何一处都不报错——
只是表现为「压缩时丢了结论字段」或「路由后工具凭空消失」这类静默缺陷。
这不是抽象不足，是**业务参数没有 colocate（就地声明）**。

## 2. 设计：spec 自带元数据，通用机制只读声明

原则（一条）：**业务层只声明「是什么」，引擎层只管「怎么组装」。**
借鉴自多 Agent 编排实践中的 ITool/IRegistry「注册即声明、不改内核」与
「领域知识按域打包、路由器保持领域无关」的组织方式（只取其组织原则，
不引入其 Evaluator/反思循环机制——本项目的调用决策由 GLM 做，见 §5）。

三个声明式字段，`ToolSpec` 与 `SkillSpec` 同构：

| 字段 | 语义 | 消费方 |
| --- | --- | --- |
| `scenes: tuple[str, ...]` | 本工具服务的意图场景（math/engineering/concept/chat）；`"*"` = 所有场景都装配 | `intent.allowed_tool_names` 动态推导装配名单 |
| `digest_fields: tuple[str, ...]` | 压缩摘要的字段优先级（`error` 永远保留） | `compress.compress_old_tool_results` 按 tool_call_id 反查工具名后取用 |
| `guide: str \| None` | 渐进式披露的场景指南文件名（prompts/ 下） | `intent.scene_guides` 去重合并后随尾部动态上下文注入 |

当前声明一览（改工具元数据时同步更新本表）：

| 工具 / skill | scenes | digest_fields | guide |
| --- | --- | --- | --- |
| `memory_search` | `("*",)` | `entities` | — |
| `kg_lookup` | math, engineering, concept | `matched` | — |
| `calculator`（sympy 缺席时兜底） | math, engineering | `value` | — |
| `code_runner` | engineering | `stdout, timed_out, returncode` | — |
| `web_search` | concept | `results` | — |
| `calculus`（skill） | math | `answer` | `guide_math.md` |
| `ode`（skill） | math | `answer, final_expr` | `guide_math.md` |
| `project_guide`（skill） | engineering | `options` | `guide_engineering.md` |

## 3. 新增一个工具的完整步骤（一处声明）

1. 在 `tools.py` 的 `_build_registry`（或 skills 目录）声明 spec：
   schema、func，**连同 scenes / digest_fields / guide 一起写全**；
2. 若声明了 `guide`，在 `prompts/` 下放对应指南文件；
3. 完事。注册、schema 透出、场景装配、压缩摘要、指南注入全部自动生效——
   `intent.py / compress.py / system.py` 一行不用改。

兜底语义（防声明缺失演变成静默缺陷）：

- 某场景装配名单推导为空 → 全量装配（路由永远不阻塞主链路）；
- 工具名解析不到 spec（如历史消息）→ `_UNKNOWN_FIELDS = (answer, value, stdout)` 通用兜底；
- `guide` 声明了但文件缺失 → 记 warning 返回空串（指南缺失不是配置错误，
  与 `Agent.md` 不同：主提示词缺失会拒绝启动）。

回归约束：`tests/test_intent.py::TestSceneDeclarations::test_registered_specs_declare_scenes`
要求任何已注册工具 / skill 必须声明 `scenes`——忘写元数据在这里爆，
而不是在线上表现为「路由后凭空消失」。

## 4. 迁移映射（旧 → 新）

| 旧（集中式，加工具要改） | 新（声明式，spec 自带） |
| --- | --- |
| `intent.py` `INTENT_TOOLS` 白名单表 | 各 spec 的 `scenes` 字段，`allowed_tool_names` 从注册表动态推导 |
| `compress.py` `_DIGEST_FIELDS` 全局字段表 | 各 spec 的 `digest_fields`；`digest_tool_content(content, fields)` 显式传参 |
| `system.load_intent_guide(intent)` 按 `guide_{intent}.md` 命名约定加载 | `system.load_scene_guide(spec.guide)` 按声明文件名加载，`intent.scene_guides` 汇总去重 |

行为等价性已验证：`pytest tests`（116 通过）+ `compress_sanity`（压缩率 92% 不变）
+ `intent_sanity`（意图分类与场景装配结果与迁移前一致）。

## 5. 借了什么、没借什么（决策记录）

**借**：注册即声明（registry 携带元数据，新工具不改内核）；
领域知识按域打包、路由器领域无关（`intent.py` / `compress.py` 现在不知道任何
具体工具名，只知道「spec 上声明了什么」）。

**不借**：Evaluator（运行时选方法）、双层反思循环 / 升级机制、工具熔断。
原因：那套机器为「代码替模型做决策」的自主任务循环设计（Worker 无人值守、
失败要自动换方法）；本项目的形态是**对话**——装配候选由 spec 决定，
真正的调用选择交给 GLM，失败直接告诉学生（学生就是升级出口，产品红线
「不追着考」决定了不能套自主升级机器）。唯一将来可能借的位置：
接入 `web_search` 等 MCP 外部工具后，为其加熔断（本地进程内工具已有硬超时，暂不需要）。

## 6. 改动检查清单

改工具元数据 / 加新工具时：

1. spec 的 `scenes / digest_fields / guide` 声明完整；
2. 跑 `pytest tests/test_intent.py tests/test_compress.py`；
3. 加了指南 → 跑 `python -m app.agent.scripts.intent_sanity`（确认注入）；
4. 动了压缩相关逻辑 → 跑 `python -m app.agent.scripts.compress_sanity`（压缩率应 ≥50%）；
5. 同步更新本文 §2 的声明一览表。
