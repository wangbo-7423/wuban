# 07 · 上下文工程设计（Context Engineering）

> 上承 [01-系统架构与Agent设计](./01-系统架构与Agent设计.md)。本文回答：**Agent 的上下文窗口是怎么管理的**——
> 每一层放什么、占多少预算、信息何时搬进搬出，以及每一项设计的实测数据。
> 对应「分层容器模型」与上下文工程五策略（Write / Select / Compress / Cache / Isolate）。

---

## 1. 设计立场

上下文工程的核心不是「把该塞的都塞进去」，而是两条：

1. **分层预算**：把窗口按功能分层（系统提示 / 记忆注入 / 历史摘要 / 近期历史 / 工具上下文 / 任务状态），
   每层设定 token 预算带，任何一层膨胀都视为缺陷；
2. **常驻 vs 按需**：每层内容先问「是不是任何话题都用得上」——是则常驻，否则按需检索（Just-in-time）。

本项目为纯 zai-sdk + 自编排 orchestrator（~200 行），**不引入 LangChain/LangGraph 依赖**，
但按其 v1 中间件的设计思想自实现等价物（映射表见 §5）。

## 2. 一次 /chat 请求的消息解剖

```
[system①] Agent.md 全文（静态主提示词，永不变更）          ┐ 静态 system 块
[system②] 静态说明（动态信息在尾部注入）                    ┘ ← 前缀缓存命中区
[*history] 最近 8 条原始卡片消息（滑动窗口）
[user]     <本轮动态上下文>                                 ┐ 尾部动态注入区
           · 当前课程                                        │
           · 场景装配说明 + 场景工具指南（渐进式披露）          │ 每轮可变，
           · 学生长期记忆（L0 常驻层 + L1 检索层）             │ 不影响前缀缓存
           · 任务状态（Scratchpad）+ 会话早期进展摘要          ┘
[user]     学生真实提问（文本 + 图片）
```

分层预算（对齐分层容器模型）：

| 层 | 预算带 | 保障机制 |
| --- | --- | --- |
| 系统提示 | 5-15% | 静态外置 `Agent.md`，靠缓存摊销成本 |
| 记忆注入 | 5-10% | L0 常驻 ~100-200 token + L1 按需 ≤5 概念 |
| 历史 | 20-40% | 最近 8 条窗口 + 滚动压缩摘要（≤700 字符） |
| 工具上下文 | 15-30% | 意图装配 3~5 个候选 + 旧轮结果一行摘要 |
| 任务状态 | 5-10% | Scratchpad 三字段，启发式生成 |

## 3. 五策略落地矩阵

| 策略 | 做法 | 实现位置 | 实测数据 |
| --- | --- | --- | --- |
| **Write**（写入持久化） | 长期记忆层：LLM 裁决抽取实体/别名/关系回写 MCP 图谱；短期记忆层：滚动压缩摘要；任务状态层：Scratchpad | `memory_service.extract_and_write`、`session_memory` | 摘要 LLM 实测保留四类信息（主题/步骤结论/误区/悬而未决）；Scratchpad 零 LLM 成本 |
| **Select**（运行时检索） | ① 记忆 L1 双通道召回（实体名+别名）；② 意图路由动态装配工具；③ `memory_search` 主动兜底 | `memory_service.get_relevant_digest`、`agent/intent.py` | 6→3~5 个工具候选；别名通道解决「FFT↔傅里叶变换」同义鸿沟（sanity 用例通过） |
| **Compress**（上下文压缩） | ①② 工具结果清除+观察遮蔽：旧轮 Observation 压成一行结论，当前轮完整；③④ 滚动摘要承接 | `agent/compress.py`、`session_memory` | 夹具压缩率 **92%**（材料量级 -81%） |
| **Cache**（提示缓存） | system 块全静态 + 动态上下文尾部注入，适配智谱隐式前缀缓存 | `system.build_system_messages`、`orchestrator.dynamic_context` | 生产链路二轮命中 **42%~89%**，命中半价 |
| **Isolate**（上下文隔离） | **刻意不做**：单 Agent 自主决策是本项目的架构立场（见 01 §1），子 Agent 拆分会引入路由/状态同步复杂度，与「陪学」的连续对话形态冲突 | — | — |

四项全部有可观测指标：`AgentResult.compressed_chars / prompt_tokens / cached_tokens`，
日志输出；分层 token 统计是后续迭代的基础。

## 4. 关键实验记录（GLM 5.3 Flash，2026-08）

这些结论直接决定了请求结构，**改结构前先重读**：

1. **隐式前缀缓存按前缀命中，且动态内容进 system 会全灭**：
   共同前缀 = 单条静态 system（~1.7K token）时命中为 0；前缀再长一点（加一条静态说明
   或带历史）即命中 ~98%。推论：任何一条 system 消息变化 → 整个 system 块作废。
2. **最小可缓存前缀存在**：SYSTEM_PROMPT 恰好卡在门槛下，因此采用「静态双 system 消息」结构
   （第二段是固定说明文案，不随轮次变化）。
3. **GLM 5.3 Flash 关不掉 thinking**：省略 thinking 参数也默认开启，reasoning 会吃光
   `max_tokens` 导致 content 为空。小任务（分类/抽取/摘要）的 max_tokens 需给 reasoning
   留足空间（实测 ≥800）。`enable_thinking=False` 只是「不主动开启」，不是「关闭」。

## 6. 提示词真源与渐进式披露

```
竞赛作品/
├── Agent.md                    # 静态主提示词唯一真源（system① 全文）
└── prompts/
    ├── guide_math.md           # 场景指南：数学计算（calculus/ode 用法）
    ├── guide_engineering.md    # 场景指南：工程实操（project_guide/code_runner）
    └── guide_concept.md        # 场景指南：概念理解（kg_lookup/memory_search 深度用法）
```

- **Agent.md**（常驻层）：身份、能力边界、八条行为规则、通用工具说明、输出卡片形态。
  由 `system.load_system_prompt()` 加载（lru_cache），文件缺失/为空直接抛错——
  提示词缺失是配置错误，宁可启动失败也不静默退化。
- **prompts/guide_*.md**（按需层）：场景专属工具的详细用法。哪个场景加载哪篇指南
  由各工具 spec 的 `guide` 字段就地声明（意图路由命中后汇总去重注入尾部动态上下文）——
  这就是 Claude Code SKILL.md 式的渐进式披露：候选少而准（工具 schema）+ 指南到位（注入文本），
  且不伤前缀缓存（同一场景内指南内容不变；换场景的缓存损失仅限尾部）。
  声明式机制的细节见 [08-工具层设计](./08-工具层设计.md)。
- **改提示词的流程**：改 Agent.md / guide_*.md → 跑
  `python -m app.agent.scripts.cache_sanity` 确认缓存命中未回退 → 跑
  `intent_sanity` / `compress_sanity` 等回归。

## 7. 决策记录

- **记忆为什么不走 embedding 检索**：实体规模小（几十个）、名字均为标准术语，
  「实体名+别名」子串匹配足够；上向量库在此规模是负收益。语义兜底由 `memory_search` 承担。
- **动态上下文为什么放尾部 user 消息而不是第二条 system**：实验 4.1 显示任何 system
  变化都会作废整块前缀；放尾部把「变化」限制在窗口末端，静态前缀得以稳定命中。
- **历史为什么用「滑动 8 条 + 滚动摘要」而不是全量 append-only**：全量 append-only
  缓存命中率最高，但历史层会无限膨胀（违背分层预算）；滑动窗口牺牲部分历史层缓存命中，
  换取窗口大小有界。保底命中的静态 system 块不受影响。
- **Isolate 为什么不做**：见 §3。
