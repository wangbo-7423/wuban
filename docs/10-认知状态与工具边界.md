# 10 · 认知状态与工具边界

> 本文回答一个架构问题：**认知心理学的业务逻辑，哪些放提示词、哪些放数据库、哪些做成 Tools？**
> 代码真源：`app/agent/tools.py`（scaffold_state / mastery_evidence）、`app/models/evidence.py`、`app/services/profile_service.py`。
> 上一篇：[09-Harness工程设计借鉴](./09-Harness工程设计借鉴.md)（工程可靠性视角）；本文是它的业务侧续篇。

---

## 1. 三层分工：教学法 × 记忆 × 手

认知科学理念在本项目里**不是**靠工具实现的，而是拆成三层，各管一段：

| 层 | 装什么 | 实现 | 为什么放这里 |
| --- | --- | --- | --- |
| **提示词层**（行为规范） | 教学法本身：学长口吻、不直接给答案、苏格拉底式反例、抛引申疑问 | `Agent.md` + `prompts/guide_*.md` | 稳定规则，每轮都生效，无状态 |
| **数据层**（学生状态） | 慢变量：topics/误区/脚手架结构/复习队列 | `learner_profiles.cognitive_state` + `conversations.summary/scratchpad` + 记忆图谱 | 跨轮持久、需审计、由确定性算法聚合 |
| **工具层**（模型的手） | 能力：查图谱、真算、跑码、查记忆、**读写认知状态** | `ToolSpec` 声明式注册 | 只有模型知道它此刻需要什么 |

关键区分：**工具是模型的"手"，不是"脑"**。教学法放 DB 或工具都会丢失每轮语境适配；状态放 prompt 则跨轮即忘。

## 2. 现状的缺口（为什么要有这两个工具）

`cognitive_state` 此前是**轮后离线重算**的，带来三个问题：

1. **实时性缺口**：学生本轮明显困惑，AI 本轮内拿不到任何状态更新，只能靠模型现判 + 通用指南；
2. **识别脆弱**：深度提问靠正则关键词（"为什么/如果/难道"），脆且浅；
3. **注入浪费**：每轮全量注入 cognitive_state，不管本轮用不用得上——违反 Select 原则（docs/07）。

## 3. 但工具化有两条红线

1. **绝不让 LLM 调工具给学生打掌握度分**——单 agent 自评不可靠（Harness Generator-Evaluator 一节论证过），且直接撞 docs/00 §6 红线：**不做应试闭环**。掌握度只能来自过程性证据聚合。
2. **确定性算法不进工具**——SM-2 复习调度、depth 估算等纯函数放轮后代码，又快又稳；做成 LLM 工具反而多花一轮调用、引入不确定性。

## 4. 分层决策 checklist

拿到任何一个"认知功能"，按序问：

```
是稳定行为规则？（怎么引导/什么语气）
  → 是：进 prompt（guide_*.md / Agent.md）
是确定性计算？（SM-2 调度/间隔/统计）
  → 是：轮后代码，绝不做 LLM 工具
是模型需要按需获取的上下文？
  → 是：读工具
是模型观察到的实时证据？
  → 是：写工具——只记「证据标签」，轮后确定性聚合
是跨轮持久的慢状态？
  → 是：DB schema
```

## 5. 两个工具的设计

### 5.1 `scaffold_state`（读口）

| 项 | 值 |
| --- | --- |
| 触发时机 | 模型拿不准引导深浅、怀疑学生学过/卡过当前话题、想避免重复纠错 |
| 参数 | `topic?`（可选，聚焦单个概念） |
| 返回 | `cognitive_load` / `scaffold_level` / `gave_answer_ratio` / 误区 top5 / 复习队列 top3 / 指定话题的 status |
| 数据源 | `learner_profiles.cognitive_state`（只读，短会话即开即关） |
| 装配 | `scenes=("*",)` 全场景；开关 `enable_scaffold_state` |

价值：把「每轮全量注入画像」变成「模型按需查询」——省 token、解决实时性，且 GLM 在 thinking 里自己决定要不要查（不写死规则）。

### 5.2 `mastery_evidence`（写口）

| 项 | 值 |
| --- | --- |
| 触发时机 | 模型**明显观察到**行为时刻时调用一次，不每轮都调（schema 里写明） |
| 参数 | `evidence_type`（受控词表）+ `topic` + `note?` |
| 受控词表 | `self_explained`（自己解释通了）/ `deep_question`（深问）/ `stuck`（连续卡壳）/ `transferred`（迁移）/ `prediction_checked`（预测→验证） |
| 落库 | `learning_evidence` 表（一行一证据：user/topic/type/note/时间） |
| 消费 | `profile_service.compute_cognitive_state` 聚合为 `topics[name].evidence = {type: count}`，**不参与状态判定/不打分** |
| 防御 | 词表校验在连库之前——GLM 发明 `score_85` 这类类型直接结构化拒绝 |

**为什么只记标签不记分数**：标签是可审计的客观行为时刻（"学生自己解释通了 PID 微分方程项"），分数是模型的主观判断。标签进画像不会把产品推向"AI 判分"的应试闭环；将来算法改进了，证据还在，可以重新聚合——这正是 Harness 警示二「数据比 harness 值钱」在教育侧的落地。

## 6. 数据流全景

```
对话中（实时）                      轮后（离线聚合）                 下一轮
┌─────────────────────┐   ┌──────────────────────────┐   ┌──────────────────┐
│ GLM 观察 → mastery_  │   │ compute_cognitive_state:  │   │ 注入策略（分层）： │
│ evidence 写标签      │ → │ 正则/词频/tool_calls/     │ → │ L0 常驻（偏好/目标）│
│ GLM 拿不准 → scaffold│   │ attempts + evidence 表   │   │ L1 按需（scaffold_ │
│ _state 查档案        │   │ → cognitive_state JSON   │   │ state 工具查询）    │
└─────────────────────┘   └──────────────────────────┘   └──────────────────┘
        写口只产标签               确定性算法（SM-2 等）            读口按需拉取
```

正则识别（`_LOAD_MARKS`/深问标记）**保留**，与工具证据互补：工具覆盖 GLM 主动观察到的时刻，正则兜底覆盖模型漏报的。两路证据在 cognitive_state 汇合。

## 7. 已知边界与后续

- `learning_evidence` 的 note 是自由文本，暂无去重/防刷——多租户生产需按 (user, topic, type) 做频控；
- 证据目前只做计数合并，不参与 `_schedule_review` 状态判定（刻意保守）；未来若要让 "stuck×3" 影响脚手架建议，走轮后确定性规则，不走 LLM 判断；
- `scaffold_state` 读的是上次聚合的快照（updated_at 可见），本轮内刚发生的 evidence 要到下轮才进档案——这是离线聚合架构的固有延迟，当前场景可接受。
