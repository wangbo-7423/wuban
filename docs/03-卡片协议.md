# 03 · 卡片协议（CardMessage）

> 对话里 AI 的每条回复都不是纯文本，而是**带类型的结构化卡片**：把「概念解释 / 数学计算 / 定理公式 / 工程实操 / 练习反馈」这些学习动作变成可点、可看、可控的实体，把认知机制（脚手架、反馈分级、证据引用、策略标签）物化成字段。
> **契约真源**：`backend/app/schemas/card.py` ↔ `frontend/src/api/types.ts` ↔ `frontend/src/components/chat/CardRenderer.vue`。

---

## 1. CardMessage 全字段

| 字段 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | `string` | 是 | — | 消息 UUID |
| `role` | `string` | 否 | `"assistant"` | 枚举 `user / assistant` |
| `card_type` | `string` | 否 | `"text"` | 17 种卡片类型，见 §2 |
| `text` | `string` | 否 | `""` | 卡片正文（支持 Markdown/KaTeX） |
| `payload` | `CardPayload \| null` | 否 | `null` | 按类型不同的动态载荷，见 §3 |
| `evidence` | `CardEvidence[] \| null` | 否 | `null` | 引证来源（透明/可解释） |
| `confidence` | `number \| null` | 否 | `null` | 本次回答的置信度 0~1 |
| `gave_answer` | `boolean \| null` | 否 | `null` | **是否直接给了答案**（引导优先留痕）。注意：标记的是「本次没直接给答案」，**不代表「出了一道题」** —— 本产品没有「AI 出题考学生」环节，见 00 §6 |
| `scaffold_level` | `string \| null` | 否 | `null` | 脚手架层级，枚举 `example / faded / hint / independent` |
| `reason` | `string \| null` | 否 | `null` | 为什么这样引导（可解释性） |
| `next_action` | `string \| null` | 否 | `null` | 建议的学生动作，枚举 `accept / adjust / reject / retry / ask / none` |
| `strategy` | `string[] \| null` | 否 | `null` | 引导策略标签：`类比 / 分解 / 反例 / 可视化`（前端渲染成小标签） |
| `thinking` | `string \| null` | 否 | `null` | GLM 思维链（thinking 模式回填，前端可折叠展示） |
| `tool_calls` | `ToolCallRecord[] \| null` | 否 | `null` | 本次调用的工具留痕 |
| `created_at` | `string(datetime) \| null` | 否 | `null` | ISO 8601 |

`CardEvidence`：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `source` | `string` | 是 | 来源（KG 节点、教材章节、课程名） |
| `page` | `string \| null` | 否 | 定位（页码/节点 id） |
| `confidence` | `number` | 否 | 来源置信度 0~1，默认 1.0 |

`ToolCallRecord`：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `tool_name` | `string` | 是 | 工具名（calculator / kg_lookup / …） |
| `args` | `object` | 是 | 调用参数 |
| `result` | `string \| null` | 否 | 结果（序列化字符串） |
| `ok` | `boolean` | 否 | 是否成功，默认 true |
| `error` | `string \| null` | 否 | 失败原因 |
| `took_ms` | `number \| null` | 否 | 耗时（预留） |

## 2. 17 种卡片类型

| card_type | 用途 | 承载的认知机制 | 前端组件 |
| --- | --- | --- | --- |
| `text` | 寒暄、过渡、引导语 | 温度、共情 | `TextCard` |
| `understand` | **概念解释 / 定理公式含义** | 认知负荷（分块）、类比建图式 | `TextCard`（结构化增强中） |
| `math` | **数学计算过程** | 分步呈现、可验证 | `MathCard` |
| `engineering` | **工程实操指导** | 脚手架、步骤化 | `EngineeringCard` |
| `question` | 反问（先问再答） | 生成效应、定位卡点 | `TextCard` |
| `practice` | **待验证的预测**（学生先猜 → AI 用工具跑出来对比）| 预测—验证探究、认知冲突 | `PracticeCard` |
| `choice` | 单/多选（概念辨析、反例题） | 采集、学生主导 | `ChoiceCard` |
| `feedback` | 对学生思路/答案的点评 | 形成性反馈（先肯定再纠错） | `TextCard`（结构化增强中） |
| `recommendation` | 下一步学习建议 | ZPD、学生主导 | `RecommendationCard` |
| `evidence` | 引证（文档/源码片段） | 透明、可追溯 | `EvidenceChips`（侧栏） |
| `progress` | **探索档案更新**（提过的好问题 / 做过的作品 / 还想深入的点）| 胜任感、成长可见 | `SidePanel` |
| `warning` | 风险提示（前置缺失/负荷过高）；判定依据 = 回答原文 + 本轮工具摘要 + 会话状态摘要（跨轮卡壳/遗留疑问是强信号）；结构化跨轮判定设计见 [17-跨轮学习状态](./17-跨轮学习状态与warning判定设计.md) | 及时干预 | `TextCard` |
| `metacog` | 元认知提示（鼓励自查） | 元认知、校准 | `TextCard` |
| `motivation` | 动机反馈（归因式鼓励） | 成长型思维 | `TextCard` |
| `scaffold_progress` | 脚手架推进提示 | 渐隐 | `TextCard` |
| `tool_call` | 工具调用中间态 | 过程透明 | `ToolTrace` |
| `interactive` | **交互可视化实验**（AI 生成可拖拽 HTML，学生亲手玩）| 具身探索、预测—验证、失谐消解 | `InteractiveCard`（沙箱 iframe，docs/16） |

> `CardRenderer.vue` 按 `card_type → component` 映射分发；未注册的类型降级为 `TextCard`。**新增一种卡片 = 加一个组件 + 注册一行 + 双端类型同步**。

## 3. CardPayload：按类型不同的载荷

`CardPayload` 所有字段可空，由 `card_type` 决定哪些字段有值：

| 字段 | 类型 | 使用者 | 说明 |
| --- | --- | --- | --- |
| `options` | `object[]` | `choice` | 选项列表，约定 `{label, value}` |
| `stem` | `string` | `question / practice` | 题干 |
| `hint_level` | `number` | `practice` | 当前已给提示层级（0 起） |
| `max_hints` | `number` | `practice` | 最大提示次数（脚手架节奏） |
| `math` | `MathBlock` | `math` | 数学块，见 §3.1 |
| `engineering_steps` | `EngineeringStep[]` | `engineering` | 实操步骤，见 §3.2 |
| `engineering_artifacts` | `object[]` | `engineering` | 配套截图/链接 |
| `interactive` | `InteractiveBlock` | `interactive` | 交互可视化块，见 §3.4（docs/16） |
| `mastery` | `object<string, number>` | `progress` | 各知识点**探索深度**（0~1）。来自**过程性证据**（自我解释 / 问题深度 / 主动迁移 / 卡点时长），**不是判分结果**，见 00 §6 |
| `risk` | `object[]` | `warning` | 风险项 |
| `meta` | `object` | 通用 | 杂项（如用户消息里的 `images`、`thinking_chars`） |

### 3.1 `math` 卡（数学计算场景）

`MathBlock`：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `problem` | `string` | 是 | 原题（LaTeX 或文本） |
| `steps` | `MathStep[]` | 是 | 分步推导 |
| `answer` | `string \| null` | 否 | 最终答案 |
| `unit` | `string \| null` | 否 | 单位 |

`MathStep`：`{ expr: string（LaTeX，KaTeX 渲染）, note: string|null（这步在干什么） }`

```json
{
  "id": "m1", "role": "assistant", "card_type": "math",
  "text": "我们用换元法一步步来：",
  "payload": {
    "math": {
      "problem": "\\int \\frac{x}{\\sqrt{x^2-1}}\\,dx",
      "steps": [
        { "expr": "u = x^2-1,\\ du = 2x\\,dx", "note": "看出根号内是 x 的二次式，整体换元" },
        { "expr": "\\int \\frac{1}{2\\sqrt{u}}\\,du = \\sqrt{u}+C", "note": "幂函数积分" },
        { "expr": "\\sqrt{x^2-1}+C", "note": "回代 u" }
      ],
      "answer": "\\sqrt{x^2-1}+C"
    }
  },
  "evidence": [{ "source": "高等数学·不定积分", "page": "ch5", "confidence": 0.92 }],
  "strategy": ["分解"],
  "gave_answer": false,
  "scaffold_level": "hint",
  "next_action": "retry"
}
```

### 3.2 `engineering` 卡（工程实操场景）

`EngineeringStep`：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `title` | `string` | 是 | 这一步做什么 |
| `command` | `string \| null` | 否 | 可执行命令/代码 |
| `expected` | `string \| null` | 否 | 预期输出（学生可自查） |
| `pitfalls` | `string[] \| null` | 否 | 常见坑 |
| `next_step_hint` | `string \| null` | 否 | 卡住时的下一步提示（先提示不代做） |

```json
{
  "id": "e1", "role": "assistant", "card_type": "engineering",
  "text": "给你一套「加一个系统调用」的实操路线，按步走，每步先看 expected 再继续：",
  "payload": {
    "engineering_steps": [
      { "title": "拉取内核源码并切换分支",
        "command": "git clone https://.../linux.git && cd linux",
        "expected": "源码目录就绪", "pitfalls": ["磁盘至少留 20G"] },
      { "title": "在 syscall 表注册新调用号",
        "expected": "arch/x86/entry/syscalls/syscall_64.tbl 多出一行",
        "pitfalls": ["改错架构目录（arm/x86 混用）"],
        "next_step_hint": "先搜索已有的 SYS_hello 所在行照抄格式" },
      { "title": "实现 sys_hello 并编译",
        "command": "make -j$(nproc)",
        "expected": "生成 vmlinux / bzImage",
        "pitfalls": ["缺少 ncurses/libssl-dev 依赖导致 menuconfig 失败"] }
    ]
  },
  "strategy": ["分解"],
  "gave_answer": false,
  "scaffold_level": "example"
}
```

### 3.3 `practice` / `question` / `choice`

> ⚠️ **`practice` 不是「练习题」**。它的正确形态是**「待验证的预测」**：
> 描述一个场景 → 让学生**先猜结果** → AI 用工具（`calculus` / `ode` / `code_runner`）真的算/跑出来 → 对比。
> 这是科学探究的「预测 → 验证」范式，**不是考试**；且**只在学生想验证自己理解时才给，不主动塞题**（见 00 §6）。

```json
{ "card_type": "practice", "text": "先别急着算——你猜一下：进程 A、B 互相等待对方释放资源，一定死锁吗？",
  "payload": { "stem": "互等资源是否必然构成循环等待？", "hint_level": 0, "max_hints": 3 },
  "strategy": ["反例"], "gave_answer": false, "next_action": "ask" }
```

```json
{ "card_type": "choice", "text": "你更想从哪个切入？",
  "payload": { "options": [
    { "label": "先讲进程", "value": "process" },
    { "label": "先讲线程", "value": "thread" },
    { "label": "直接对比", "value": "compare" } ] },
  "strategy": ["可视化"] }
```

**作答闭环（practice / choice 通用）**：学生经 `POST /api/student/practice/submit`（见 02 §4.1b）
提交作答后，原卡 `payload.meta` 追加留痕，前端据此渲染「已提交」状态与历史作答：

```json
{ "payload": { "meta": {
  "answered": true,
  "attempts": [ { "answer": "B", "at": "2026-08-29T07:48:04Z" } ] } } }
```

- `attempts[].answer`：practice 卡为作答文本；choice 卡为所选项 `value`；
- 学生作答同时以 user 消息入流（`payload.meta.practice_ref = {card_id, card_type}`），
  随后跟一张 `feedback` 审阅卡（先肯定 → 指出问题并说明原因 → 抛引申疑问，不打分）；
- 提交次数回推 `cognitive_state.practice.submissions`（过程性证据，非分数）。

### 3.4 `interactive` 卡（交互可视化，docs/16）

AI 生成的**自包含可拖拽 HTML 实验**（沙箱 iframe 渲染）。由 `make_visual` 工具触发、
切卡阶段**确定性注入**（HTML 不经过切卡模型——模型上下文里只有工具小结）。

`InteractiveBlock`：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `html` | `string` | 是 | 自包含 HTML（CSS/JS 全内联，**零外部请求**），≤64KB |
| `preview_text` | `string \| null` | 否 | 一句话说明能拖什么、看什么 |
| `probe` | `InteractiveProbe \| null` | 否 | 预测→验证引导：`{question, reveal_hint}` |
| `meta` | `object \| null` | 否 | `{source: template\|llm, template, params, title}` |

```json
{
  "id": "v1", "role": "assistant", "card_type": "interactive",
  "text": "动手试一试（拖动看看会发生什么）：",
  "payload": {
    "interactive": {
      "html": "<!doctype html>…",
      "preview_text": "拖动 Kp / Ki / Kd，实时看阶跃响应曲线",
      "probe": { "question": "把 Kp 拉到最大，曲线会变成什么样？先猜，再拖。", "reveal_hint": null },
      "meta": { "source": "template", "template": "pid_tuner", "params": {"kp": 2, "ki": 0.5}, "title": "PID 调参实验台" }
    }
  },
  "strategy": ["可视化"]
}
```

安全约定（前端渲染侧）：`sandbox="allow-scripts"` 且**不带** `allow-same-origin`；
后端守门：体积 ≤64KB、模板源码零 `http(s)://` 引用（`test_viz.py` 锁死）。

## 4. 枚举与约定

| 枚举 | 取值 | 用于 |
| --- | --- | --- |
| `ScaffoldLevel` | `example / faded / hint / independent` | 脚手架从「看样例」渐隐到「独立做」 |
| `NextAction` | `accept / adjust / reject / retry / ask / none` | 建议的学生下一步 |
| `strategy` 标签 | `类比 / 分解 / 反例 / 可视化` | 引导策略（见 00 §5），可多选 |

## 5. 当前实现状态（诚实说明）

- **协议完备、双端类型已对齐**；`math`/`engineering`/`choice` 等结构化卡片的前端渲染组件已就位。
- **结构化装卡已启用**：`backend/app/agent/cards.py` 的 `format_cards()` 用 GLM JSON mode
  把最终回答切成 1~3 张卡，主卡 + `extras` 多卡一并落库回传（原启发式 `_pick_card_type()` 已删除）。
- **已知缺口**：输出模板尚未要求模型产出 `reason` / `next_action` / `evidence`；
  `mastery` / `scaffold_level` 等认知字段仍无写入点（掌握度未落库、侧栏恒空）。
- **练习闭环已通**：`practice`/`choice` 卡支持作答提交（`/api/student/practice/submit`）：
  作答留痕进 `payload.meta.attempts` → `feedback` 审阅卡落库 → `cognitive_state.practice` 回推。
- 持久化时整卡 JSON 落 `messages` 表（见 [04-数据库设计](./04-数据库设计.md)），历史回读还原为同一结构；
  **卡片 id 与库内消息主键一致**（`add_message` 透传 `CardMessage.id`），按 card_id 的交互刷新后不失配。
